# superfluid 0.1.11

**A lone request prefills in larger chunks.** When one request has the server
to itself, its prompt now goes to the engine in chunks of up to 4096 tokens,
where it went in chunks of 512. On an M5 Pro, Qwen3.6-35B-A3B at Q4 on the
basert runtime prefills 1k-token prompts at 3950 tokens a second where it took
3058, and 8k-token prompts at 3624 where it took 3149. `/v1/completions`
now honours `stop` and streams each token as it is produced, llama.cpp
b12244 is the build `superfluid runtime install llamacpp` installs, and
superfluid installs from PyPI.

## New

- **superfluid on PyPI.** Each release is now published to PyPI as
  [`superfluid-cli`](https://pypi.org/project/superfluid-cli/), beside the
  install script, Homebrew, npm and crates.io:
  `pipx install superfluid-cli`, `uv tool install superfluid-cli` or
  `pip install superfluid-cli`. It is the same prebuilt release, one wheel
  for macOS 15 or later on Apple silicon and one each for Linux on x86-64
  and arm64 with glibc 2.28 or later, and puts `superfluid` on your `PATH`.
  It has no Python API and needs nothing from your Python beyond running
  the command; the runtimes still install under `~/.superfluid`, never into
  your Python environment. `superfluid self update` runs pipx's or uv's own
  upgrade (`pipx upgrade superfluid-cli`), asking first, and leaves a pip
  install to pip (`pip install --upgrade superfluid-cli`). The name is
  `superfluid-cli` because `superfluid` on PyPI is an unrelated project.
  See [Homebrew, npm or PyPI](https://github.com/basecompute/superfluid/blob/v0.1.11/docs/getting_started/installation.md#homebrew-npm-or-pypi).
- **`--basert-neural-engine on|off`.** The basert runtime's first option on
  `serve`: `off` runs every prefill on the GPU alone, for an engine that
  splits the prefill between the GPU and the Neural Engine on Apple silicon.
  The default, `on`, leaves the engine to decide. BaseRT 0.4.6, the newest
  release, prefills on the GPU alone and has no such switch, so with it `on`
  changes nothing and `off` fails the load.
  See [basert options](https://github.com/basecompute/superfluid/blob/v0.1.11/docs/models/runtimes.md#basert-options).
- **A pulled model's Neural Engine programs are compiled ahead.** With an
  engine that can, a model pulled by id has the programs its prefill runs on
  the Neural Engine compiled right after the pull, by the worker that will
  serve it, so its first prompts do not prefill on the GPU alone while they
  compile (about 30 seconds for a 27B model). macOS keeps them for each
  executable, so the first start after a Superfluid upgrade compiles them
  once more. Nothing is compiled with BaseRT 0.4.6, or with
  `--basert-neural-engine off`.

## Changed

- **A lone request's prefill.** With one request running, nothing queued and
  room for another, its prompt now goes to the engine in chunks sized to
  about four seconds of prefill, at most 4096 tokens (2048 before the
  engine's prefill rate is known), where it went in 512-token chunks. A
  request that arrives meanwhile waits out at most one such chunk. Mean time
  to the first token on the M5 Pro above: 0.284 s for 1k-token prompts where
  it was 0.362, 2.37 s for 8k-token prompts where it was 2.73.
- **llama.cpp b12244** is the build `superfluid runtime install llamacpp`
  installs; b12219 and b12207 are tested builds too, and b12125, b12102,
  b12068, b11981, b11951, b11925, b11890, b11889, b11642 and b11284 stay.
  Builds from b12191 on, which lay out llama.cpp's context parameters
  differently, load; before, Superfluid refused them.
- **The docs** at [superfluid.sh](https://superfluid.sh) move to the same
  site as the BaseRT docs. Old addresses redirect to the new pages, and the
  install command they give is
  `curl -fsSL https://basecompute.co/sf/install.sh | sh`
  (`https://superfluid.sh/install.sh` still works).

## Fixed

- **`stop` on `/v1/completions`.** Stop strings were ignored and the text
  ran on to `max_tokens`. The text now ends where the first stop string
  starts, with `finish_reason` `"stop"`, streamed or not, as on
  `/v1/chat/completions`.
- **A streamed completion sends each token as it is produced.** On
  `/v1/completions` the first token waited for the end of an engine step, one
  decode round late: on an M5 Max with Qwen3.8-27B, a 1k-token prompt's first
  token now arrives in 951 ms where it took 983. With `logprobs` the
  stream still sends text a step at a time.
  See [Completions](https://github.com/basecompute/superfluid/blob/v0.1.11/docs/serving/openai_compatible_server.md#completions-and-fill-in-the-middle).
