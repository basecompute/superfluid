# superfluid 0.1.13

**A `json_schema` response format that names no schema is refused.** A
chat completion that asked for structured output with a `json_schema`
holding only a `name` was served without any constraint; it is now a 400,
as on the Responses API. llama.cpp b12408 is the build
`superfluid runtime install llamacpp` installs, superfluid falls back on
BaseRT 0.5.0 when it cannot read BaseRT's release listing, and the docs and
help text describe superfluid as it is today.

## Changed

- **llama.cpp b12408** is the build `superfluid runtime install llamacpp`
  installs; b12359 is a tested build too, and b12317, b12283, b12244,
  b12219, b12207, b12125, b12102, b12068, b11981, b11951, b11925, b11890,
  b11889, b11642 and b11284 stay.
- **BaseRT 0.5.0 without the release listing.** superfluid installs the
  newest BaseRT release it can drive, found through BaseRT's release listing
  on GitHub. When that listing cannot be fetched (offline, or when GitHub's
  API refuses the call), it falls back on the releases pinned in superfluid
  itself, and the newest of those is now 0.5.0, where it was 0.4.0. On
  Linux x86-64 with
  a Strix Halo, Strix Point or Gorgon Point GPU, that fallback now has the
  ROCm engine to install; before, it had none. `superfluid runtime versions`
  and `superfluid compat` list 0.5.0.
- **The docs, the README and the help** describe superfluid as an
  open-source server that runs LLMs on your own hardware, from one machine
  or several that act as one server, and their examples serve
  `basecompute/Qwen3.8-27B` on BaseRT. Every docs page was checked against
  the code: among the corrections,
  [security](https://github.com/basecompute/superfluid/blob/v0.1.13/docs/deployment/security.md)
  now says fleet links are encrypted with the fleet token, where it said
  they were plaintext, and lists the daily check for a new release as
  network traffic. The install script suggests `basecompute/Qwen3.8-27B`
  when it installed BaseRT.
- **`superfluid stop --help`** says what the command does: it sends the
  server SIGTERM, which ends it without draining (requests in flight are
  cut), and waits up to 90 seconds for it to exit. To let it finish what is
  in flight, send `kill -USR1 <pid>` instead. The command itself is
  unchanged.

## Fixed

- **A `json_schema` that names no schema.** On `/v1/chat/completions`,
  `"response_format": {"type": "json_schema", "json_schema": {"name": "planet"}}`,
  with no `schema`, was read as if `{"name": "planet"}` were the schema,
  which constrains nothing, so the reply was unconstrained. A `json_schema`
  holding only `name`, `description` and `strict`, or nothing, is now a 400
  that names `json_schema.schema`. A schema given directly as `json_schema`,
  without the `schema` wrapper, is still accepted.
  See [structured outputs](https://github.com/basecompute/superfluid/blob/v0.1.13/docs/features/structured_outputs.md).

The engine ABI is unchanged: superfluid 0.1.13 serves BaseRT 0.5.0 and the
0.4 releases as 0.1.12 does.

See [installation](https://github.com/basecompute/superfluid/blob/v0.1.13/docs/getting_started/installation.md)
for every way to install superfluid, and
[updating](https://github.com/basecompute/superfluid/blob/v0.1.13/docs/serving/updating.md)
for how each is updated.
