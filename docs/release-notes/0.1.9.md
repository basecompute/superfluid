# superfluid 0.1.9

**A release in sizes pulls its Medium.** `superfluid serve
basecompute/Qwen3.8-27B-BaseQuant-V1`, with the llamacpp or the basert runtime,
now serves the Medium of a repository whose model files are named by size and
none by quant, and `:small` takes another size. Before, the llamacpp runtime
took whichever file Hugging Face's manifest handed back for `latest` (the
Large, 20.8 GB) and the basert runtime needed `--pull-file`. And llama.cpp
b12125 is the build `superfluid runtime install llamacpp` installs, with a
refusal of an untested build that says where it stands to the tested ones.

## New

- **A release in sizes.** A repository whose model files are named `-XS`,
  `-Small`, `-Medium`, `-Large` and `-XL`, as the BaseQuant repositories are,
  is pulled by its Medium when nothing names a file, with either runtime:
  `superfluid serve basecompute/Qwen3.8-27B-BaseQuant-V1 --runtime llamacpp`
  serves `Qwen3.8-27B-BaseQuant-V1-Medium.gguf` and `--runtime basert` the
  `.base` of the same size. A size tag takes another (`:small`, `:xl`),
  `--pull-file <name>` a file, and a size the release does not come in names
  the ones it does. The llamacpp runtime reads the repository's listing from
  the Hub for this (`HF_TOKEN` goes with the request, as for a gated model);
  a listing that fails leaves a plain pull to llama.cpp with a warning, and
  `--offline` spells the file from the size without one. A quant-named
  repository, or a quant tag (`:Q4_K_M`), is left to llama.cpp as before. The
  basert runtime serves a size from the install that records that file, and
  passes a size to basert 0.4.2–0.4.4, which take none, as the file's name.
  See [Pulling models by id](https://github.com/basecompute/superfluid/blob/v0.1.9/docs/models/supported_models.md#pulling-models-by-id).

## Changed

- llama.cpp b12125 is the build `superfluid runtime install llamacpp`
  installs; b12102 is a tested build too, and b12068, b11981, b11951, b11925,
  b11890, b11889, b11642 and b11284 stay.
- `superfluid runtime install llamacpp --version bNNNN` for a build the
  adapter was not tested with said "its C API may differ — pass --untested to
  install it anyway" whatever the build, though most builds are not listed
  (the nightly tests one a day at most, and llama.cpp tags fifteen to
  thirty-five) and one between two tested builds very likely has their C API.
  The refusal now says where the build stands: between two tested builds, and
  so very likely theirs, or newer than the newest or older than the oldest,
  where it may differ. Either still installs only with `--untested` and is
  checked at load. `superfluid runtime versions llamacpp` lists the tested
  builds, and the
  [runtimes page](https://github.com/basecompute/superfluid/blob/v0.1.9/docs/models/runtimes.md#per-runtime-installs)
  now says so where it named one build.
- The nightly that tests each new llama.cpp build walks back from one that
  fails: it tries the next-newest build the recipe does not list, at most five
  below the one the night began on, and the first to pass is the one proposed.
  Before, a build upstream fixed a few builds later held the recipe at its
  last tested build until the next night that passed, six nights in a row in
  late October. See
  [How an upstream release becomes a tested one](https://github.com/basecompute/superfluid/blob/v0.1.9/docs/models/runtimes.md#how-an-upstream-release-becomes-a-tested-one).
