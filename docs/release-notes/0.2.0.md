# superfluid 0.2.0

**superfluid runs on Windows, and a fleet's nodes do what a single server
does.** Windows x86-64 has a release and an installer of its own and
serves GGUF models through llama.cpp, alone or in a fleet with macOS and
Linux machines. In a fleet, a node now serves several models, speculates
by default on BaseRT, takes the engine flags `superfluid serve` takes and
reports its counters to the head. A request with images no longer stalls
the requests running beside it, and llama.cpp on a Mac no longer fails
every request for a small model served at a large context window.

## New

- **Windows.** In PowerShell,

  ```
  irm https://github.com/basecompute/superfluid/releases/latest/download/install.ps1 | iex
  ```

  installs superfluid on Windows 10 (1803 or later) and Windows 11,
  x86-64, without administrator rights and with nothing to install first.
  `npm install -g @basecompute/superfluid` and `pip install superfluid-cli`
  install it there too. It serves GGUF models through llama.cpp:
  `superfluid runtime install llamacpp` takes the CUDA build where an
  NVIDIA driver is found, the Vulkan build where a Vulkan driver is, and
  the CPU build otherwise. `superfluid self update` and `superfluid self
  use <version>` keep releases side by side, as on macOS and Linux, and
  `serve --tui`, `superfluid top` and `--log-format json` work there. A
  Windows machine can be a fleet's head or one of its nodes: a fleet of a
  Windows, a Linux and a macOS machine, each serving Qwen3-0.6B, answered
  96 of 96 concurrent requests with the head on each of the three in turn.
  Other machines reach a Windows head only where Windows Defender Firewall
  allows it, which an administrator grants once; a Windows node that joins
  with `superfluid node join` needs no rule. BaseRT and MLX models, a
  Homebrew package and Windows on ARM64 are not available yet. See
  [Windows](https://github.com/basecompute/superfluid/blob/v0.2.0/docs/getting_started/installation.md#windows).
- **A node serves several models.** `superfluid node join --model a
  --model b` (and `superfluid-noded` likewise) serves each model on its own
  engine, with their context windows sized together as `superfluid serve`
  sizes several models on one machine. The head runs each request on the
  model it names. Give `--model-name` once per `--model`. A node started
  with no `--model` still follows its head's one model. See
  [several models on one node](https://github.com/basecompute/superfluid/blob/v0.2.0/docs/serving/distributed_serving.md#several-models-on-one-node).
- **Fleet nodes speculate by default on BaseRT.** Since 0.1.14 `superfluid
  serve` uses speculative decoding by default for BaseRT models, but a
  fleet's nodes decoded plainly and had no flag to change it. A node now
  speculates as `serve` does, downloading the paired drafter unless
  `--offline` is given, and `superfluid node join` and `superfluid-noded`
  take `--speculate`; `--speculate off` decodes plainly. With head and node
  on one M5 Max serving Qwen3-8B, two 400-token requests decoded at 62 and
  81 tokens per second by default and at 52 and 47 with `--speculate off`.
  As on `serve`, greedy output is not always word for word the plain
  output unless `--spec-bitexact` is set.
- **Engine flags on nodes, sampling defaults on the head.** `superfluid
  node join` and `superfluid-noded` take the engine flags `serve` takes:
  `--kv-bits`, the runtime options such as `--basert-neural-engine`,
  `--prefill-budget`, `--tick-decode-budget`, `--tick-target-ms`,
  `--park-lossy`, `--park-budget-gb`, the `--spec-*` options and the
  `--otlp-*` options. A fleet head now accepts `--repeat-penalty`,
  `--presence-penalty` and `--spec-max-temperature` and applies them as a
  single server does: a request's own value still wins. Give engine flags
  to the nodes; a head that is given one, such as `--kv-bits`, ignores it.
- **QoS in a fleet.** A fleet head accepts `--http-default-qos`,
  `--no-http-qos-header` and `--http-allow-batch-invariant`, and a key
  policy's `class` and `max_class` apply there. A batch-invariant request
  is sent to a node of this release, which runs it alone; when no node
  serving the model can, the head answers 400 `unsupported_on_fleet` and
  names the nodes. `--class-lanes` is set on each node (`superfluid node
  join --class-lanes`), not on the head. See
  [QoS](https://github.com/basecompute/superfluid/blob/v0.2.0/docs/serving/distributed_serving.md#qos).
- **A head's `/metrics` counts what its nodes do.** A head's scheduler
  counters, such as `superfluid_spec_proposed_total`,
  `superfluid_spec_accepted_total`, `superfluid_warm_prefix_tokens_total`
  and `superfluid_preemptions_total`, stayed at 0 because the nodes do the
  work. Each node now reports its counters: the head adds them into its
  own series and lists them per node as `superfluid_fleet_node_<counter>_total`
  with the `node`, `addr` and `model` labels. The sums keep counting when
  a node restarts or leaves.
- **`superfluid stop --drain`** asks a server to stop accepting
  connections, finish what is in flight and exit, and waits until it has;
  `--pid <pid>` names a server you started yourself. It is what `kill
  -USR1 <pid>` does on macOS and Linux, and Ctrl+Break in the server's
  console on Windows.
- **`--basert-npu <on|off>`** is a second name for
  `--basert-neural-engine`, for BaseRT engines that share prefill with the
  NPU of an AMD Strix machine. No released BaseRT engine does so yet; the
  option and what such a machine needs are described in
  [runtimes](https://github.com/basecompute/superfluid/blob/v0.2.0/docs/models/runtimes.md)
  ahead of one.

## Changed

- **A request with images no longer stalls the requests beside it.**
  superfluid encoded all of a request's images, and then prefilled its
  whole prompt, before the other running requests got their next tokens.
  Images are now encoded between decoding steps and prefilled one image at
  a time. On an M6 Mac mini serving gemma-4-26B-A4B, the longest pause in
  a streaming chat beside a request with 8 images went from 8.3 seconds to
  0.7. The image request's own first token comes later when other requests
  are running, there from 14.4 seconds to 16.8, and is unchanged when it
  runs alone.
- **Faster sampling on x86-64.** The sampler's passes over the vocabulary
  were vectorized on Apple silicon only. On a Ryzen AI Max+ 395, sampling
  a token from a 152k-token vocabulary now takes 165 µs where it took 289,
  and Qwen3-4B Q4_K_M on llama.cpp's Vulkan build serves eight concurrent
  sampled requests at 225 tokens per second where it served 204. A seeded
  request samples the same tokens as before.
- **llama.cpp b12535** is the build `superfluid runtime install llamacpp`
  installs on macOS and Linux, and b12503 on Windows. A build now counts
  as tested on the platforms it was run on: one tested elsewhere only is
  refused by name and installs with `--untested`. b12503, b12470, b12435,
  b12408, b12359, b12317, b12283, b12244, b12219, b12207, b12125, b12102,
  b12068, b11981, b11951, b11925, b11890, b11889, b11642 and b11284 stay
  on macOS and Linux, and b12470 on Windows.
- **The fleet protocol is version 4**, which names the model each request
  is for. Heads and nodes of 0.2.0 and of earlier releases still work
  together, so a fleet can be updated one machine at a time: an older head
  sees a node's first model only, an older node serves its one model as
  before, reports no counters and is sent no batch-invariant request.

## Fixed

- **llama.cpp on a Mac failed every request for a small model at a large
  context window.** With llama.cpp builds from b12059 on, a context that
  shares one cache between its lanes reserves working memory on Metal that
  grows with the cache, which superfluid did not count. On a 48 GB Mac,
  Qwen3-0.6B at its automatic 40,960-token window was given more memory
  than the GPU has and every request failed. The cache is now sized by
  what its whole context takes on the device, measured when the model
  opens (about 70 ms): 95k tokens there, where 208k was attempted. A fixed
  `--max-context 16384` or `--max-batch 1` was not affected.
- **No token from a decoding step the GPU refused.** When Metal ran out of
  memory during a llama.cpp step, a token sampled from that step's
  leftover data could be streamed to the client before the request
  failed. Such a step now fails with nothing sent, and the server's log
  gives llama.cpp's reason.
- **Requests with two or more images on BaseRT.** With released BaseRT
  engines, through 0.5.2, a request whose images sit close together in the
  prompt could fail with a 500 (`scheduler tick failed`); on BaseRT 0.5.0
  with gemma-4-E2B, requests with 2, 4 and 8 images all did. They are
  served now.
- **A refusal reaches a client that is still uploading.** A request
  refused for its key or its rate limit (401, 403 or 429) while its body
  was still arriving could see the connection reset instead of the answer.
- **Images of a cancelled request are released.** A request with images
  that was cancelled before it started kept its encoded images in memory.
- **npm: Ctrl+C at start-up.** With superfluid installed from npm, a
  signal that arrived just as the launcher started the program could end
  the launcher and leave the program running.

## Known issues

- On Windows, llama.cpp's CUDA builds have not been run on a machine with
  an NVIDIA GPU, and its ROCm build is installed only by name
  (`superfluid runtime install llamacpp --backend rocm`).
- Image requests on Qwen3.6-35B-A3B still start only once the requests
  that are running have finished.

The engine ABI is unchanged: superfluid 0.2.0 serves BaseRT 0.5.2 and the
0.5 and 0.4 releases as 0.1.15 does.

for every way to install superfluid, and
