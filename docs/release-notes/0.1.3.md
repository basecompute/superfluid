# superfluid 0.1.3

**superfluid can update itself.** `superfluid self update` installs a new
release beside the current one, checks that it starts and can use any baseRT
engine in use, and makes it current. The version it replaced stays
available to switch back to; a running server keeps its own copy. This release
also makes runtime compatibility explicit, exposes the runtimes' own settings
on the command line, and adds support for newer llama.cpp and MLX releases.

## New

- **Updates.** `self check` checks for a newer compatible release, `self list`
  shows the copies installed, and `self use <version>` switches to one already
  here. `superfluid serve` checks for updates once a day after the server is
  ready, waiting three days after a release is published before announcing it;
  `self update` can install it as soon as it is out. `--offline` or
  `SUPERFLUID_NO_UPDATE_CHECK=1` disables the background check. It never restarts
  the server or installs an update on its own.
- **Compatibility records.** `superfluid compat [--json]` describes what each
  shipped adapter was built and tested for. Releases include `compat.json` in
  each tarball and attach a copy per platform beside it, plus the baseRT engine
  ABI number in an asset name. A product hosting superfluid can choose a
  compatible release before downloading it. `superfluid runtimes --json`
  reports the loaded runtime's ABI and, for baseRT, what this build requires.
- **Runtime versions.** `superfluid runtime versions <id> [--json]` lists the
  versions an adapter installs on its own, newest first, which can run on this
  machine and which are already installed. The listing comes from the adapter's
  recipe without a network request. `superfluid runtimes` adds an `INSTALLABLE`
  column; its JSON adds `installable`.
- **Runtime settings.** `serve` accepts the runtimes' own options as
  `--<runtime>-<name> <value>`: llama.cpp's GPU placement, cache types, loading,
  threading and RoPE settings, and MLX's prefill chunk, cache limit and Python
  environment. `superfluid runtime options <id>` lists them even before the
  runtime is installed. Values outside the declared bounds and options given
  twice are refused before a worker starts.
- **Newer runtimes.** llama.cpp b11642 is supported alongside b11284, including
  the context-parameter layout introduced in b11480. MLX 0.32.4 with mlx-lm
  0.32.0 is supported alongside MLX 0.32.2 with mlx-lm 0.31.3; the adapter drives
  the newer cache layout and preserves its settings when cloning or exporting
  state.

## Changed

- A baseRT engine is accepted by its ABI number when it states one, beginning
  with baseRT 0.4.0; its release version no longer has to match this build's
  major.minor. Engines from 0.3.x, which predate the number, remain accepted.
  Required functions are still checked when the library loads, and newer
  engines' model configurations are read by size so the struct can grow without
  changing the ABI. `runtime install basert` selects an engine with the matching
  ABI, or a 0.3.x engine; another requires `--untested`.
- The install script keeps releases under `$SUPERFLUID_HOME/versions/` and
  links the commands in the install prefix to the current copy. The first
  `self update` migrates an older install-script installation and keeps its
  workers while a server still uses them. Homebrew, `cargo install` and source
  builds continue to be updated through the way they were installed.
- `serve` exits with **4** when a model's runtime is missing or cannot run on
  this machine. That is distinct from a usage error (**2**) and an installation
  it tried that failed (**1**), so a host can decide whether to install a runtime
  or report a failure.
- The retired `--prefill-chunk` flag now points to the runtime-specific
  `--mlx-prefill-chunk` and `--llamacpp-ubatch-size` options.

## Fixed

- On machines without an accelerator, llama.cpp's prefix cache now keeps
  exported state in host memory within an 8 GiB budget. It previously treated
  the missing device's free memory as zero and kept no exported state.
- A superfluid started through a symlink or a shim on `PATH` finds its workers
  and adapters beside its real executable. Switching the current release no
  longer makes an already running server lose track of its own workers.

See [updating superfluid](https://github.com/basecompute/superfluid/blob/v0.1.3/docs/serving/updating.md)
and [hosting superfluid in another product](https://github.com/basecompute/superfluid/blob/v0.1.3/docs/serving/hosts.md)
for the update and compatibility contracts.
