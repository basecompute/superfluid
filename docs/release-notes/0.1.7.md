# superfluid 0.1.7

**A fleet head is the server one machine runs.** Every API format and route
superfluid serves on one machine now answers through a fleet head, over as
many models as the nodes serve, and the head needs neither the weights nor a
runtime. `Idempotency-Key` on any POST makes a retry safe, on one machine and
on a head. A conversation stays on the node that has it warm, across a node
or head restart. Each token through a head costs what it costs on the node
alone; a request pays 50–100 ms once, before its first token.

## New

- **Every format and route over the fleet.** A head answers OpenAI chat,
  completions and responses, Anthropic messages and Ollama `/api/chat` and
  `/api/generate`, streaming or not, with tools, structured output,
  `logit_bias`, `logprobs` and the penalties, and embeddings, LoRA, images,
  audio and transcription, each as a single machine answers it: the same
  handlers run on the head, and each generation's decode loop runs on a node.
  Before, a head served chat completions for one model and refused the rest.
  See [Distributed serving](https://github.com/basecompute/superfluid/blob/v0.1.7/docs/serving/distributed_serving.md).
- **Many models, and a head without the weights.** Give `--model` once per
  model; a request's `model` picks the nodes serving it and `/v1/models`
  lists each. A model given by id (`superfluid serve org/model:tag --fleet …`)
  is not pulled: the head takes its tokenizer and chat template from the first
  node serving it and needs no runtime installed. A node whose tokenizer
  differs from the head's for a model gets none of its requests.
- **`Idempotency-Key`.** Send one with any POST, in any API format, and send
  the same request with the same key to retry it: the first request's answer
  comes back whole, from its start, marked `Idempotent-Replayed: true`. A
  connection that drops mid-stream does not stop the generation, a finished
  answer is kept for 24 hours and replayed after a restart, and a request a
  restart cut short runs again. The same key with another body or route is
  refused with 422. See
  [Retrying with Idempotency-Key](https://github.com/basecompute/superfluid/blob/v0.1.7/docs/serving/openai_compatible_server.md#retrying-with-idempotency-key).
- **Warm conversations on a fleet.** The head sends a conversation's next
  turn to the node that ran it, while that node has a lane free, and remembers
  this across its own restart. `superfluid node join --park` (and
  `superfluid-noded --park`) keeps each prompt's prefix on disk, so a node
  that restarts starts the conversation warm. With Qwen3 4B and a 9.3k-token
  conversation, a next turn on an M4 Pro node takes 0.39 s warm against
  19.1 s cold, and 1.6 s after the node restarts with `--park`; on a GB10,
  reading a prefix back is slower than prefilling it, and the docs say when
  `--park` pays off.
- `GET /health` on a head answers 503 `no_nodes` while no node that is up
  serves a model, with `nodes_up` and `nodes_known` and each model's own
  count. A request for a model no node is up for is 503 before any stream
  starts.

## Changed

- A fleet under load: a new session takes a node lane no generation holds
  rather than the next in turn, and a node runs a generation in the QoS class
  the head gave it rather than one prefill per tick. On an M4 Pro node with
  8 requests at once, the median first token fell from 6–7 s to 0.8 s and
  throughput rose from 95 to 139 tokens/s, what the machine does alone.
- llama.cpp on a GB10: a cache entry leaving the pool is exported to host
  memory only where that is cheaper than prefilling it again, and a sequence
  moving between buffers passes through one kept buffer instead of a freshly
  zeroed one. One GB10 with 16 users went from 131 to 191 tokens/s, with the
  median first token from 15.6 s to 8.1 s; the same applies on one machine.
- A head asks each node for one connection beyond its lanes, so a prompt's
  encoding or a state operation goes through while every lane is generating.
  A node from 0.1.6 opens only its lanes and still works.
- A fleet head refuses a batch-invariant lane, however it is asked for, with
  400 `unsupported_on_fleet`: a node batches each generation with the others
  it runs.
- llama.cpp b12068 is the build `superfluid runtime install llamacpp`
  installs; b11981, b11951, b11925, b11890, b11889, b11642 and b11284 stay.
- Installing with cargo: `cargo install superfluid` builds no baseRT worker,
  so `superfluid runtime install basert` stops with "no
  superfluid-worker-basert to install the basert runtime with". The
  installation page now adds `cargo install superfluid-adapter-basert`, which
  puts the worker beside `superfluid`.

## Fixed

- A chat prompt with `enable_thinking: false` and no system message carried an
  extra `system` turn on a template that drops the empty system message
  (Qwen3.8): the user's turn was taken for the system body. A user message is
  also trimmed where the template trims it (Qwen3.5, Qwen3.8), so leading or
  trailing newlines tokenize as the template renders them.
- A fleet node whose last connection dropped stayed up in the head's view, so
  nothing dialed it again: a node that restarted under another `--model-name`
  kept its old name, was passed over for it and never served again. It is now
  marked down, and the head's retry reconnects and learns what it serves.
- The same image arriving in several requests at once failed to store on a
  node, and on a node that ended the link. Each write now has its own
  temporary file, and a blob a node cannot keep fails only its request.
- 0.1.6 reached GitHub and crates.io but not npm or the Homebrew tap: the
  install test that gates those uploads still expected 0.1.5's `superfluid
  self update` wording. It takes 0.1.6's, so this release reaches every
  channel.
- Three tests that failed CI on a loaded runner, one OS leg at a time, hold
  under load; the one change to shipped code is that `self update` starts the
  package manager with the crate's retry on a binary another process still
  holds open.
