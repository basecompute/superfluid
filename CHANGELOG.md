# Changelog

## 0.1.7

- 0.1.6 reached GitHub and crates.io but not npm or the Homebrew tap: the install test that gates those uploads (`packaging/try-install.sh`, run by publish.yml on each release) still expected 0.1.5's `self update --dry-run` wording, "was installed by <manager>; `<command>` updates it", and 0.1.6 says "was installed by pip, which updates it: run `<command>` (…)" for a pip copy and "was installed by <manager>: `self update` would run …" for the managers it runs itself (#54). The test now takes both: the manager named either way, a dry run that exits 0 showing the command it would run, one that exits 1 naming it (pip; npm too in the test, whose throwaway `--prefix` has no npm of its own), and the copy unchanged after it; `packaging/README.md` says so. Nothing else changes from 0.1.6.

## 0.1.6

- A fleet node's link stays up while the node generates: each end sends a keepalive after 5 s with nothing sent and gives the link up (`TimedOut`) after 30 s with nothing heard, both inside `pump`, so any loop reading the link keeps it alive mid-generation; a generation runs on a thread of its own and its tokens reach the connection's loop through a channel (coalesced as before, 16 tokens or 200 ms) while the loop reads cancels, lease grants and heartbeats and sends status every 2 s; the head bounds its wait on a node. Link version 3, offered beside 2: a peer on 2 sends no heartbeat and is never given up for silence. Before, a generation longer than the node's idle timeout (120 s) had its link dropped when it finished, one longer than its lease (60 s) hung the request, and a node that went quiet without closing its socket hung the head's request for good; the stopgap that reset the idle clock after a generation and renewed leases from the token loop is gone (#55).
- `superfluid self update` on a copy a package manager installed runs that manager's own update after asking (`--yes` skips the question and is required without a terminal; `--dry-run` shows the command; `--version` is refused). The command comes from the manager's name in `installed-by` (or the path, for packages from before the file), and the manager binary is the one that owns the copy — the `brew` of its Cellar, the `npm` of its global folder with that `bin/` first on PATH, the `cargo` beside it; pipx and uv by their venv paths. A pinned formula, another user's Homebrew, an npm global folder that needs root, a project's npm dependency and pip in an environment are named, not run, and nothing runs while a superfluid server runs from the copy. The superfluid basert installs beside itself is marked basert's (`installed-by`) and left to `basert self update` (#54).
- A request's decode is timed per tick: the scheduler stamps each lane once per tick, after the engine returns, with the tokens it has produced, and a request's decode is the tokens after its first tick over the time from that tick's end to the last tick's end — the event-based figure's definition, measured once per tick instead of once per delivered `Generated` event, which a tick that hands a lane several tokens at once (reasoning tags, channel changes) left missing or inflated. `LaneEvent::Done` and `GenerateOutcome` carry `decode: (tokens, seconds)`, `access_log` uses it, and `decode_round_secs` counts only decode rounds (a lane whose prefill ends in the tick is not a round). `ttft=` and `prefill=` are unchanged (#51).
- `superfluid runtime remove`, `repair` and `use` read `<id>@<install>` as `<id> <install>`, the form `superfluid runtimes` lists; naming the same install both ways is accepted, two different installs are refused, and `install`, `update`, `versions` and `options` say they take only the id (`install`'s error gives the flags for the named build). `installs::remove(id, None)` uses the install the id names rather than the runtime's whole package directory, so a misspelled install fails with `has no install` and deletes nothing. `remove <id>` with more than one install needs `--all`. The parse lives in `cli::runtime_target` (#56).
- `superfluid runtimes`: INSTALLABLE agrees with `runtime install` — the kit's `Runtime::unlisted()` states an adapter's rule for versions it does not list (basert: with no version it installs the newest release stating engine ABI 1), the worker's `versions` carries it as `unlisted`, and an install made without `--untested` of a version newer than every listed one counts as installable, `(installed)` in the table and newest first in `runtime versions`; DEVICE is the memory budget; WORKER is short. `--json` keeps the paths and figures (#57).
- A baseRT bundle whose speculator head is `kind: gemma4-mtp` — Google's Gemma 4 MTP head embedded whole by `basert add-speculator`, which the engine builds as the separate sidecar and drafts over the target's KV — is an MTP head to bare `--speculate mtp-head` and to `auto`'s first choice, beside `mtp`; the "carries no speculator head" refusal names `basert add-speculator`. The kind is not `mtp` so that a release before this one leaves such a section alone (#60).
- llama.cpp b11981 is the build `superfluid runtime install llamacpp` installs; b11951 and b11925 are tested builds too, and b11890, b11889, b11642 and b11284 stay (#48, #53, #59).

## 0.1.5

- A fleet head announces itself on the local network: its mDNS service name was one byte over the 15 the registry allows, and the refusal reached no one, so `superfluid node join` with no address found nothing on macOS or Linux; the host is announced as one label (macOS's name already ends in `.local`). The head serves `GET /metrics` with a series per node (`superfluid_fleet_node_{up,lanes,lanes_active,queue_depth,pool_blocks_used,pool_blocks_total,decode_tokens_total}`, labelled `node` and `addr`), counting tokens as they arrive and taking each node's KV pool and queue from the status it sends; `superfluid top <head>` shows one row per node and follows nodes as they join and leave, and `superfluid top` with no address finds the head through the HTTP port its announcement carries.
- llama.cpp b11890 and b11889 are tested builds, and `superfluid runtime install llamacpp` installs b11890; b11642 and b11284 stay.
- MLX 0.32.4 with mlx-lm 0.32.2 is tested and the version installed; 0.32.2 with mlx-lm 0.31.3 stays.
- A baseRT model named with its variant (`org/model:<variant>`) that is installed already is served as it is, as `--offline` serves it: `serve` no longer runs `basert pull`, which takes no variant and fetched the default quant instead, and failed for a repo that has none, such as a `file-…` variant taken with `--pull-file` (`no pre-converted .base for quant "q4"`). `--pull-force` still pulls.
- A baseRT model named with a variant that is not installed is pulled as that variant where basert takes one (0.4.2 and later): `serve` runs `basert pull org/model:<variant>`, so a catalog variant such as `default-f16`, or a `file-…` variant, is fetched as named rather than as the default quant, and `--pull-file` is no longer needed to serve one beside other models. `--pull-file`, `--pull-profile` and `--pull-target`, which basert refuses beside a variant, are left out of that pull; `--pull-revision` and `--pull-force` go with it. An older basert, or one whose `--version` names no version, is given the id alone, as before.
- Each release is also published to npm (`@basecompute/superfluid`, with one package per platform) and Homebrew (`basecompute/tap/superfluid`), repackaged from the release tarballs by `.github/workflows/publish.yml` and `packaging/`. A package carries an `installed-by` file at the release's root; `superfluid self update` leaves such a copy to its package manager and names the command that updates it, as the line `serve` prints for a newer release does. Before, a package's layout read as the install script's in-place copy, which `self update` would move under `~/.superfluid/versions`.
- release.yml builds every crate from its packaged form in a `crates-verify` job before the crates.io upload, which runs no build script, and the jobs that publish are pinned to action commits and Rust 1.99.1.

## 0.1.4

- `superfluid serve` takes `--pull-file <name>` for a baseRT model: one `.base` from a repo that holds several, such as one whose files are named by size (`Foo-Medium.base`) rather than by quant. It is passed to `basert pull --file`, and the model is served from the install `basert list --json` records that file in. It needs basert 0.4.1 or later.
- `superfluid runtime install basert`, and a `serve` that installs it first, take the newest baseRT release this build drives, as 0.1.3 said they did: it installed the newest pinned one (0.3.0), and a newer release only with `--sha256`. The engine's digest is the one GitHub lists for it; the pins, now with 0.4.0, answer offline.

## 0.1.3

- A libbaseRT is judged by its engine ABI number: baseRT 0.4.0 and later state one (`baseRT_abi_version()`), and a library whose number equals the one this build was built for serves whatever its version says. A 0.3.x library states none and serves as the line that carried this ABI before it was numbered. The check at load still verifies every function; the model configuration is read by size from a library of 0.4.0 or later (`baseRT_get_config_into`), so the struct may grow without a new number, and by value with a size check from an older one.
- `superfluid runtime install basert` picks an engine by the ABI number baseRT publishes beside each bundle (`basert-engine-abi-<N>.txt`): the newest release with this build's number, or a 0.3.x engine, and another only with `--untested`.
- `superfluid compat [--json]` prints what this build was built and tested for, per runtime, and each release carries the same as `compat.json` beside its tarball, so a host can choose a release before downloading it: for basert the header version, the ABI number, the line accepted without one and the engines it installs on its own; for llama.cpp and MLX the upstream versions each shipped adapter installs on its own. An adapter declares its part with the `Runtime::compat` method, and its worker answers `compat --json`; `superfluid compat` exits 1 when a shipped adapter does not, so a release with a broken adapter is not published. `superfluid runtimes --json` reports a ready runtime's `abi` and, for `basert`, `requires`.
- `superfluid runtime versions <id> [--json]` lists the versions an adapter installs on its own, newest first: which install on this machine and as what, and which are installed. `superfluid runtimes` gains an `INSTALLABLE` column, the newest such version here, and `installable` in its JSON. A worker answers `versions` from its recipe alone; the `Runtime::versions` method plans each tested version by default.
- `superfluid self update` installs the newest release that fits this machine beside the current one, under `$SUPERFLUID_HOME/versions/<v>`, proves it starts, and makes it current; the version it replaced stays for `superfluid self use`, older ones are removed, and a running server is never touched. `self check`, `self list` and `self install` go with it; the install script now places a release the same way, and a copy it placed before is migrated by its first `self update`. `superfluid serve` says once a day, after the server is up, when a newer release is out (`SUPERFLUID_NO_UPDATE_CHECK=1` or `--offline` turns it off). Releases carry the engine ABI number in an asset name, `superfluid-basert-abi-<N>.txt`, and `compat.json` is now attached to the release as documented.
- `superfluid serve` exits 4 when the runtime for the model is not installed or cannot run here, distinct from a usage error (2) and from an install it tried that failed (1).
- A runtime's own knobs are given to `serve` as `--<runtime>-<name> <value>`: llama.cpp's model and context parameters (`--llamacpp-n-gpu-layers`, `--llamacpp-flash-attn`, `--llamacpp-cache-type-k`, `--llamacpp-load-mode`, the RoPE and YaRN settings, 26 in all) and the MLX executor's (`--mlx-prefill-chunk`, `--mlx-cache-limit-mb`, `--mlx-venv`). An adapter declares them with `Runtime::options`, the daemon checks each value against the declaration, its bounds included (`--llamacpp-threads` at most 512, a batch at most 2^20 tokens, a RoPE frequency at least 0), before a worker starts and refuses an option given twice, and `superfluid runtime options <id>` lists them, before the runtime is installed too; `superfluid runtimes --json` carries them as `options`.
- superfluid finds its workerd and adapters beside its real executable, so a symlink or a shim on `PATH` keeps the worker process.
- llama.cpp b11642 is installed and tested beside b11284: from b11480 `llama_context_params` has a second layout, which the adapter reads by the build it loads, and a build whose parameter structs outgrew the layout it declares is refused at load.
- MLX installs mlx-lm 0.32 beside 0.31: the shim drives 0.32's caches, whose state carries their settings, and prices, clones and exports a rotating or chunked cache by the tokens it holds.
- On a host without an accelerator, llama.cpp's prefix cache keeps state beyond the pool in host memory within 8 GiB, as it does with the model on the CPU by choice; it kept nothing, having read the free memory of a device the host does not have as none.
- [Hosting superfluid in another product](docs/serving/hosts.md) documents the contract a host builds on.

## 0.1.0

First public release.

- `superfluid serve <model>`: one daemon serving GGUF files through llama.cpp, MLX directories through MLX and `.base` bundles through the baseRT engine, each runtime installed on first use.
- OpenAI-compatible chat, completions, embeddings, files, batches and Responses API; Anthropic Messages API; Ollama API; a native session API over a unix socket and WebSocket, with a Python client (`clients/python`).
- Continuous batching with QoS classes, per-key policy, rate limits and preemption of background work by interactive requests.
- Durable sessions in a write-ahead log: fork, resume after a restart, survive a worker crash.
- Prefix caching, KV parking, speculative decoding, tool calling and structured outputs.
- Prometheus metrics, OTLP traces and metrics, structured logs and a terminal monitor.
- Fleet mode: one head serving the HTTP API over several nodes.
