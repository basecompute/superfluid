# Changelog

## 0.2.0

- windows: superfluid builds for Windows x86-64, with the MSVC or the GNU Rust toolchain, and serves GGUF models through llama.cpp as an ordinary user. It did not build there: `cargo check --target x86_64-pc-windows-gnu` stopped in `superfluid-shm` (34 errors) and at about a hundred more in the daemon, because Link W rode unix socket pairs a worker inherits by descriptor number, a shared-memory segment was a POSIX shm fd passed with `SCM_RIGHTS`, and the daemon called libc directly for file locks, random bytes, the host's name, `dup2`, `exec`, `setsid`, `kill` and symlinks. `superfluid-shm` gains an `os` module that names a unix stream socket (std's on Unix, `uds_windows`' on Windows, which has had `AF_UNIX` since 1803) and a segment's handle (a descriptor, or a section handle). A Windows segment is an unnamed section backed by the paging file, passed by duplicating its handle and writing the duplicate's value with the sender's process id (the receiver moves it into itself with `DUPLICATE_CLOSE_SOURCE`). A Windows child inherits no sockets, so the daemon binds a socket under a random name in the temporary directory and starts the worker with `--link <socket>`, to which the worker connects its two streams; Unix keeps `--frames-fd` and `--fd-channel-fd`. The daemon's new `sys` module holds what it asks of the system beyond std, once for each system: the exclusive lock, random bytes, the host's name, an owner-only file, whether a process lives, ending one, a detached start, and running a program in this one's place. `runtimes/<id>/current` is a file holding the default install's name on Windows, where an ordinary user may make no symbolic link; `canonical` drops the `\\?\` Windows puts before a resolved path; the directory flush after a rename is Unix-only (the Responses API stored nothing there: `io: Access is denied`); `sys::open_private` gives the fleet token, the web token, media, telemetry and session exports mode 0600 on Unix and an access list of their own on Windows. Timed reads: Winsock's `SO_RCVTIMEO` cancels the read when the time is up, and a read cancelled as bytes arrive fails with `WSAEINTR` or `ERROR_IO_PENDING`, which Link W's 5 ms and Link F's 20 ms polls met within a minute; on Windows a read now first waits that long for the socket to be readable (`WSAPoll`), and decode speed is as it was (Qwen3-0.6B Q4_K_M, Radeon 8060S, Vulkan: 316.4 to 316.9 tok/s, 312.4 to 317.0 with Winsock's timeout). `dial` asks a socket for its peer before it clones it: a clone made right after a connect with a timeout refused `shutdown` (`WSAENOTCONN`, 548 times of 3,000 in a probe, none after), so a node changing its model could wait on a lane for good. Not on Windows: baseRT and MLX (no engine there, so the daemon builds with `--no-default-features --features llamacpp,tui`), a Homebrew package and ARM64. The tests that stand in for a worker with a `#!/bin/sh` script or for a link with a symlink are `#[cfg(unix)]`; a `.gitattributes` keeps text LF in every checkout. CI gains a `windows-2025` job (clippy, build and test of the daemon and of the fourteen other crates that build there), with `TMP` and `TEMP` on the runner's work disk, where a synced append takes 0.13 ms against 3.34 ms on its system disk. A fleet of release builds on Windows (Vulkan), Ubuntu 26.04 x86-64 (ROCm) and an M4 Pro Mac (Metal), Qwen3-0.6B Q4_K_M on each, with the head on each of the three in turn: 96 of 96 requests at once answer, and 12 streams of 1,200 tokens all complete with a node killed 1.5 s in (#162).
- windows: draining, the console, and versions side by side. Windows has no signal to send a process, so a server waits on an event named for its process id. `superfluid stop --drain` sets it (and sends `SIGUSR1` on Unix, so the command is the same everywhere) and waits for the server to exit; `--pid` names a server that is not `launch`'s; Ctrl+Break in a server's console asks the same. A worker started with `--link` answers Ctrl+Break by doing nothing and ends when its server closes its streams: the key reaches every process on the console, and it ended the worker under the generation the drain was there to finish (a 500 with `forcibly closed (10054)`; now a 200 with all 1,500 tokens, then "drained" and exit 0). `--log-format json` relays stderr through a pipe set with `SetStdHandle`, and `events::exit` drains the relay before `ExitProcess`, which runs no `atexit` function, so the `error` event of a failed start is no longer lost there. `serve --tui` and `superfluid top` build and run on Windows (the capture of stderr goes through `sys`). `superfluid self update`, `use`, `install` and `list` keep releases under `$SUPERFLUID_HOME\versions\<v>` as elsewhere: `current` is a file holding the version's name, and each command on `PATH` is a copy of `libexec\superfluid\superfluid-shim.exe` (a `shim` feature of the daemon crate, so `cargo install` builds none), which runs the current version's program of its own name with its arguments, console and exit status, inside a job object so that ending the launcher ends the program. A launcher on `PATH` is replaced only by a newer revision, and a version a server runs from is kept. A node with no `--model` that starts again for its head's new model has no `exec` on Windows and starts the next node as a child; it now ends each of its daemons first, on every platform (the next node ended after three seconds with "the session log ... is already open in another session store", and the old model's worker stayed loaded) (#162).

Docs: a Windows row and section in `installation.md`, `quickstart.md` and `cli.md` (draining, `self`), `design/adapters.md` (`--link`), `distributed_serving.md` (other machines reach a Windows head or `superfluid-noded` only where Windows Defender Firewall lets them in, and a rule for the head's TCP ports alone leaves it unfound by a node that starts after it, which asks on UDP 5353), and the eight pages that named macOS and Linux alone (#170, merged into #162's branch). `tools/suite` runs on Windows. - llama.cpp: a shared KV pool is sized by what its context takes on the device. On an Apple-silicon Mac a small GGUF at a large window failed every request (`unsloth/Qwen3-0.6B-GGUF:Q4_K_M` at the auto window of 40,960 for 8 lanes and at `--max-context 32768`, on M4 Pro and M5 Pro Macs with 48 GB; 16384 and `--max-batch 1`, which still fit a KV buffer per lane, worked). The adapter sized a shared pool to 60% of the device memory the weights left free with a cell priced at its KV bytes, but since b12059 llama.cpp's Metal attention over a unified cache reserves one layer's K and V rows of every cell for each of the context's sequence ids, and the adapter asks for 32: 136 kB a cell beside 115 kB of KV for this model, a context of 52 GB on a device whose working set is 40 GB. Metal allocates past the device and reports its free memory as zero, so the check after the context exists gave back only the headroom's worth of cells (208k to 190k). `superfluid-executor::sizing` gains `ContextCost` (bytes whatever the size, and bytes a cell, from what two contexts of different sizes took) and `fitted_cells`; the adapter measures that cost on two small contexts (2,048 and 4,096 cells, or `n_batch` and twice it where that is more) before it makes a shared pool, about 70 ms more to open this model (0.22 s to 0.29 s), and makes the pool once at its size: 95k tokens "at the 251 kB a token takes on Metal (115 kB of it KV cache)". It measures only where the device's free figure is one the adapter sizes windows by (Metal, and CUDA with a dedicated GPU), a measured cell is never priced under its KV, and a trial llama.cpp does not make or the free figure does not follow is halved down to a batch and then given up, never failing the open. Not run on CUDA; Vulkan, ROCm and integrated GPUs keep the old pricing. - sampling: the row maximum and the softmax pass run in SSE2 on x86-64. Both passes over a row of logits were NEON on AArch64 and scalar loops everywhere else, so on x86-64 sampling a token cost more than twice what it does on Apple silicon and a greedy pick ten times as much. `max_of` and the row pass in `softmax_weights` gain an SSE2 form under `#[cfg(target_arch = "x86_64")]` (SSE2 is in the x86-64 baseline, so there is no detection and no branch), and `exp_neg_x4` gets an x86-64 version that is the scalar `exp_neg` operation for operation, each lane bit for bit, so a seeded request samples the same tokens as before; a NaN in the row is passed over, as `v > best` and NEON's `maxnm` pass over one. ## 0.1.0

First public release.

- `superfluid serve <model>`: one daemon serving GGUF files through llama.cpp, MLX directories through MLX and `.base` bundles through the baseRT engine, each runtime installed on first use.
- OpenAI-compatible chat, completions, embeddings, files, batches and Responses API; Anthropic Messages API; Ollama API; a native session API over a unix socket and WebSocket, with a Python client (`clients/python`).
- Continuous batching with QoS classes, per-key policy, rate limits and preemption of background work by interactive requests.
- Durable sessions in a write-ahead log: fork, resume after a restart, survive a worker crash.
- Prefix caching, KV parking, speculative decoding, tool calling and structured outputs.
- Prometheus metrics, OTLP traces and metrics, structured logs and a terminal monitor.
- Fleet mode: one head serving the HTTP API over several nodes.
