# Changelog

## 0.1.12

- basert: superfluid installs BaseRT's ROCm engine on Linux x86-64 with an AMD Strix Halo (gfx1151) or Strix Point / Gorgon Point (gfx1150) GPU. BaseRT 0.5.0 publishes one ROCm bundle for both, `basert-engine-linux-x64-rocm-<v>.tar.gz`, linked against ROCm 10 at `/opt/rocm/core-10.0`; `basert` already installed superfluid's x86-64 build beside it, but someone who installed superfluid first (`install.sh`, `superfluid runtime install basert`) was refused on x86-64. The kit's `Host` gains `amd_gpus`, the LLVM targets the KFD driver reports (`/dev/kfd` plus each topology node's `gfx_target_version`: 110501 → gfx1151, 110500 → gfx1150), in the order HIP numbers them: `hip_view` models ROCr's `ROCR_VISIBLE_DEVICES` filter (set but empty = no GPU, trimmed entries, `strtol` base 0, a bad, out-of-range or repeated entry ends the list) and then HIP's `HIP_VISIBLE_DEVICES` (else `CUDA_VISIBLE_DEVICES`; plain decimals; a bad entry ends it, a repeat is skipped), and a UUID entry leaves the order unknown (`amd_order_unknown`). It also gains `rocm_runtimes`, the real `/opt/rocm/core-<version>/lib` trees (the `core` and `core-10` links ROCm 10 adds through `/etc/alternatives` are not counted twice); both show in `describe()` (`Linux x64, AMD gfx1150, ROCm 10.0`) and `to_json()`. The basert recipe maps Linux x64 whose HIP device 0 is a gfx1151 or gfx1150 to `linux-x64-rocm` (with the order unknown, any Strix GPU, and the engine checks device 0); a Strix GPU behind another one is refused with `HIP_VISIBLE_DEVICES=<n>` to pick it (`amd_hip_indices`, its index among ROCr's list), another AMD GPU or none with the three supported platforms and both targets named, and a release's ROCm engine without `/opt/rocm/core-10.0` with what to install (a bundle given with `--from` is not checked, since it may be built against another ROCm). `--backend` on the basert runtime is a check, not a choice: one engine runs on a machine, and a mismatch says "baseRT's engine runs on X here, not Y". The adapter's `devices()` reported every Linux engine as `CUDA`; it says `ROCm` on x86-64, with `AMD gfx1151` as the name when there is no NVIDIA model. `scripts/install.sh` runs `superfluid runtime install basert` on x86-64 Linux when `/dev/kfd` exists and carries on as on arm64 when the GPU is not one the engine runs on; `scripts/build_runtime_adapters.sh` runs the basert worker's starts-and-reports check on the x86-64 build too. The recipe gets BaseRT 0.5.0's pin, with its three assets (macOS arm64, Linux arm64 CUDA, Linux x64 ROCm), at release; `the_pins_are_whole` accepts the third. Tests: `linux_x86_64_with_a_strix_gpu_takes_the_rocm_engine`, `backend_rocm_is_the_strix_engine_and_refused_elsewhere`, the kit's `an_amd_gpu_is_named_by_the_target_its_kfd_node_states`, `rocm_runtimes_are_the_core_trees_with_libraries_under_the_root` and the `hip_view` cases; on strix-point-1 (gfx1150, ROCm 10) the worker's `plan` picks `linux-x64-rocm` and `check` against a local ROCm libbaseRT reports `{"backend": "ROCm", "name": "AMD gfx1150"}` (#118).
- serve: a route that answers without its request body reads the body first. The Ollama management routes (`/api/pull`, `/api/push`, `/api/create`, `/api/copy`, `/api/delete`, `/api/blobs/{digest}`, 501 `unsupported_management`) and `POST /slots/{id}/save|restore` (501 `slots_retired`) answered before reading it; hyper then makes one attempt to read the rest and closes the connection when the body has not all arrived, so a client that sends the head and the body in separate writes (ureq can) met a reset instead of the 501, which on macOS fails the client's next `setsockopt` with `EINVAL` (`fleet_head_api` failed once that way on a macos-15 runner). `drain_body` (`http_state.rs`) reads a body to its end, up to 1 MiB, and drops it; a larger one (an `/api/blobs` upload) is still left to hyper's close. `ollama_api`'s `a_bodyless_answer_waits_for_a_body_sent_after_its_head` sends the head, sees no answer within 300 ms, then sends the body and gets the 501 (#115).
- tui: the `superfluid serve` monitor's log pane scrolls by screen rows. `render_log` clamped a copy of the offset while the stored one kept growing, so after scrolling past the top (or `g`, which set it to `usize::MAX / 2`) Down, PgDn and the wheel did nothing until the slack was worked off; the pane took the last N lines for N rows and let them wrap, so a long line pushed the newest ones off the bottom while following; and the offset counted back from the newest line, so a scrolled-up view moved with every line that arrived. `LogView` keeps the offset in wrapped rows and clamps it on every draw, `log_window` wraps by display width per grapheme cluster (`unicode-segmentation` 1, `unicode-width` 0.2, ratatui 0.29's measure) and copies only the visible rows out of the ring, and rows that arrive while scrolled up are added to the offset. PgUp / PgDn step a page less one row (was 10 lines), `Home` and `G` join `g` and `End`, and queued input is drained before a redraw. The ring (`telemetry.rs`, now `LogLines`) numbers lines through eviction and cleans them on the way in: a carriage return keeps what follows it, ANSI escapes and other control characters go, tabs become spaces, and a multi-line event becomes one line per line. Ten `tui::log_pane_tests` (two draw through ratatui's `TestBackend`) and two `telemetry::log_ring_tests` (#116).
- llama.cpp b12317 is the build `superfluid runtime install llamacpp` installs; b12283 is a tested build too, and b12244, b12219, b12207, b12125, b12102, b12068, b11981, b11951, b11925, b11890, b11889, b11642 and b11284 stay (#117, #119).
- Dependencies: the GitHub Actions group (8 updates) and the docs site's `sharp`, `next` and `source-map-js` (#110, #111, #112).

## 0.1.11

- superfluid is published to PyPI as `superfluid-cli` with each release, beside the install script, Homebrew, npm and crates.io: `publish.yml`'s `pypi` job uploads the three wheels `packaging/python/build_wheel.py` builds (macOS 15+ arm64, manylinux 2.28 x86-64 and aarch64, each the release tree under `superfluid_cli/release/` with launchers for the commands) through the trusted publisher on the `pypi` environment, and skips a version whose wheels are all on PyPI. 0.1.10's wheels, uploaded 2026-11-10, were the first. `docs/getting_started/installation.md`'s "Homebrew, npm or PyPI" gives `pipx install superfluid-cli` (or `uv tool install`, `pip install`) and the upgrade commands, and the public note announces it (#109).
- A lone lane's open prefill tick is a whole engine chunk. With one live lane, nothing queued and a lane slot free, every prefill tick is open (a request could join it), and on the basert runtime it stayed at 512 tokens: the open cap waits for two ticks to teach the prefill rate, but a lone dense prompt is fused into the engine's decode rounds, which report no prefill phase, so the rate was never learned and every prompt was cut into 512-row chunks; once it was learned, the 1024-token open cap (`OPEN_PREFILL_TICK_MAX`) still held a fast MoE model to a quarter of the engine's chunk. A lone lane's open tick is now 2048 tokens until the rate is taught (`OPEN_PREFILL_TICK_LONE_UNTAUGHT`), then sized to 4 s (`OPEN_PREFILL_TICK_SECS_LONE`) in 512-token steps, at most 4096 (`OPEN_PREFILL_TICK_MAX_LONE`, the engine's largest chunk); shared lanes and queued work keep the old caps, and a request that arrives during a lone tick waits out at most that tick. Qwen3.6-35B-A3B Q4 with a DFlash drafter on basert, M5 Pro, two alternating rounds of six prompts a bucket: 1k prompts prefill 3058 → 3950 tok/s (mean TTFT 0.362 → 0.284 s), 8k prompts 3149 → 3624 tok/s (2.73 → 2.37 s). `prefill_order_tests` covers the lone cap at ~300, ~600 and ~3000 tok/s (#100).
- `/v1/completions`: a streamed completion sends each token as it is produced, and `stop` is honoured. The stream sent text only from committed events, at the end of an engine tick, so a lone prompt's first token waited behind that tick's decode rounds (Qwen3.8-27B on basert, M5 Max, one 1k-token prompt: 983 ms to the first token at `max_tokens` 2, 951 at 1); without logprobs it now follows the lane's partial emits as a chat stream does (`generate_streaming_delta`), and with logprobs it still follows the commits, which carry the spans the logprobs pair with. The request had no `stop` field, so stop strings were dropped and the text ran on to `max_tokens`; it now takes `stop` as a string or a list, as chat does: generation is cancelled once a stop string is produced, the text ends where the first one starts with `finish_reason` `"stop"`, and a stream holds back a tail that could open a stop string until the next text settles it. `openai_api` tests: streamed text equals non-streamed text with and without logprobs, `stop` cuts at the first stop string streamed and not, and a stop string that never appears changes nothing (#105).
- basert: `--basert-neural-engine <on|off>` (default `on`), the runtime's first `serve` option. `off` calls the engine's `baseRT_set_neural_engine(0)` before the load, so every prefill runs on the GPU alone; `on` leaves the engine's default, which splits a prefill between the GPU and the Neural Engine on Apple silicon where that is faster. The symbol is resolved as optional: an engine without it still loads, and asking it for `off` is an error at load rather than an option silently ignored. No published baseRT exports the switch yet (0.4.6 runs every prefill on the GPU), so with 0.4.6 `off` fails the load and `on` changes nothing. Served on an M5 Max with Qwen3.8-27B Q4 against an engine with the split: the split is built at load with the default and not with `off` (#103).
- basert: a pulled model's Neural Engine programs compile in the worker that will load it, ahead of its first load. An engine with `baseRT_prepare_neural_engine` compiles a model's split programs once per Mac and macOS version (about 30 s for a 27B on an M5 Max), and a load that finds them uncompiled compiles them in the background while the GPU runs the prefill alone, so the first prompts after an install prefill on the GPU only. The ANE service keeps a compilation per executable, by its code-signing identifier, so after a successful pull `pulls::pull` runs the built-in worker as `superfluid-workerd ahead --engine <id> --model <path>` (the kit's `Runtime::ahead`, a no-op by default), best effort: a failure is said and the first load does the work. The engine builds the programs for the prefill chunk, which it sizes by the context window (a Qwen3.5/3.6 MoE on an M5 with 40 GiB or more to plan with takes a 16384-row chunk from a 16384-token window, 4096 below), so `ahead` passes `--max-context` to the call, and without one (a pull, before any serve picks a window) prepares both ends, the window a load given 0 picks and the model's trained one (`TokenizerHandle::trained_context`), which cover every window between. Nothing is done with `--basert-neural-engine off`, on an engine without the call (every published baseRT so far) or for a model the split takes nothing of. Each superfluid build's worker has its own identifier, so the first start after an upgrade compiles once more. Against an engine with the call on an M5 Pro, Qwen3.8-27B Q4: a cold `ahead` compiled 7 programs in 58.7 s, and a second run of the same worker found them compiled in 0.1 s; `neural_engine_ahead` (set `BASERT_TEST_MODEL_ANE`) checks that windows sharing a chunk share its programs (#106).
- llamacpp: the adapter drives the context-parameter layout llama.cpp b12191 introduced. b12191 (ggml-org/llama.cpp#30966) added `float moe_cache_cpu_share` after `moe_cache_size` in `llama_context_params`, which with its padding moves every later field by eight bytes; neither layout the adapter knew (b11284's, b11480's) fits, so it refused every build from b12191 on at load (the designed outcome, rather than driving the wrong struct), and the nightly failed on b12197 to b12202 on Metal and CPU alike. `sys.rs` adds `llama_context_params_v3` with its default-params and init functions under it, and `ContextLayout::V3`, told from the defaults after V1 and V2 are tried; the worker fills it the same way. Tests pin the V3 offsets, read a b12191 image built from the b11480 one as V3, and read a V3 library's defaults into the V1 names `the_tested_build_is_laid_out_as_declared` checks (#99).
- llama.cpp b12244 is the build `superfluid runtime install llamacpp` installs; b12219 and b12207, the first tested builds past b12191's layout, are tested builds too, and b12125, b12102, b12068, b11981, b11951, b11925, b11890, b11889, b11642 and b11284 stay (#95, #104, #107).
- The nightly keeps a CUDA build whose minor version moved upstream. llama.cpp b12184 published its CUDA 13 build as `cuda-13.5` where every earlier build said `cuda-13.4`; `nightly_runtimes.py append` carries the previous tested build's asset names to the new build, so it found none of the four CUDA 13 archives and recorded the build without them (linux with a 580+ driver would have been offered CUDA 12.8), and the recipe tests, which named `cuda-13.4`, failed on every runner. `append` now builds the list in `carried_assets`, which follows a name it cannot find to the newest archive of the same backend and major version (any minor, compared as numbers) and prints the move; a new major is still reported missing. The recipe tests take the CUDA 13, CUDA 12 and ROCm names from the newest tested build and fail naming the build when one is missing. Six `carried_assets` cases in `tests/scripts/test_nightly_runtimes.py` (#97).
- Docs: superfluid.sh moves from MkDocs to the Next.js site the baseRT docs use, in `docs-site/`, which renders `docs/` at build time (nothing synced or generated is committed). GitHub Pages publishes it as before: a push to `main` builds `/dev/`, a `v*` tag `/<major.minor>/` and `/latest/`, each a static export under its own base path, with `install.sh`, `CNAME`, the root redirect and a `404.html` at the root; old MkDocs URLs (`/latest/serving/cli/`) redirect to the new routes (`/latest/cli/`). `docs.yml` builds the site on PRs and fails on a broken relative link or a `docs/` page missing from `docs-site/src/docs-manifest.mjs`, as `mkdocs --strict` did. `docs/README.md` is a short overview instead of a link index, and the install command the docs give is `curl -fsSL https://basecompute.co/sf/install.sh | sh` (`superfluid.sh/install.sh` is still published). The Pages workflow first runs when this release reaches `main` (#102).

## 0.1.10

- `--speculate auto` on the `basert` runtime takes the drafter the hub catalog marks for the target (`speculator_auto` on a sidecar row, beside `speculator_for` and `speculator_rank`) ahead of the bundle's own MTP head, and pulls it with the target's runtime when no copy is installed (its `default-q4` file, never with `--offline`; a failed pull is said and `auto` settles among what is here), for every model served: the first, the others given with `--model`, and the ones loaded later through `--model-dir` or `/v1/models/load`. The catalog marks Qwen3.8-27B and Qwen3.6-35B-A3B with their DFlash2 drafters, which `auto` passed over for the in-bundle head: Qwen3.8-27B Q4 on an M5 Pro, quick tier coding / math / qa at 128 tokens, 53.2 ms a token plain, 27.1 / 22.0 / 24.7 with the head, 21.3 / 11.1 / 18.3 with DFlash2. macOS only, where the pairings were measured; Gemma 4's embedded head (`gemma4-mtp`) stays first; the head and the other fitting drafters remain the fallbacks, in their old order (`speculate_resolve::auto_ranked`; the pull is `resolve_all`'s, which each of those paths passes its own) (#89).
- Streamed tool calls arrive at token cadence: a call's `function.arguments` fragments come from the lane's partial emits, token by token, as `content` and `reasoning_content` already did, where they rode on committed events, and a lane commits once a tick. On the basert runtime a tick grants at least 32 tokens (`NATIVE_TICKS`), so a call shorter than that arrived whole; llamacpp and mlx tick every few tokens, which hid it there. The XML tool wire (`<function=f><parameter=k>v</parameter></function>`, which auto-detection serves Qwen3.5, 3.6 and 3.8 with through the curated ChatML codec) now streams too: the codec takes its fragment mode from the template it takes the wire from, so a call's name goes out as soon as `<function=…>` closes and its arguments one at a time, typed from the request's schemas. Before, the JSON fragmenter ran over XML text: every XML call reached the client whole once it closed, on every runtime, and a call whose argument opened with a JSON object (writing a `package.json`) streamed under that object's `"name"` (`demo` for `write`), which a client that keeps the first name it sees (pi, under Local) could not run; the JSON fragmenter now opens only on a body whose first value is an object. Each streamed call is finished at its own close, in source order: a second call in the same tick no longer feeds the first one's fragmenter (on the XML wire the first took the second's arguments), text after a call no longer goes out before the call's last fragment (the Responses adapter closed such a call without its `}`), and a call that never opened or did not parse is settled at its close as its commit would have. `--tool-call-parser` naming the model's own envelope no longer wraps the codec (`json` on an XML model parsed XML as JSON). A call opened before any of its text is committed has the id `call_<generation>_<index>`. Non-streaming responses were not affected (#88).
- A model pulled by id shows its progress on stderr, the same for every runtime: a bar with the percentage, the bytes of the total, the rate over the last five seconds and the time left, redrawn in place on a terminal and a line every ten seconds elsewhere, a note once every byte is here and the tool is still verifying, converting or copying, and one line left behind with the fetch's size, time and rate. Before, `llama download` drew its bar only when stdout was a terminal, `basert pull` drew none, and `snapshot_download` printed a file at a time. The adapter kit's `progress` module watches the directories the runtime's tool writes into, four times a second, and counts the regular files written since the watch began (links and what was cached already are not counted; huggingface_hub 2.x's hub-wide `blobs/` store is watched too). Totals are looked up before the tool runs, best effort: llamacpp from the Hub manifest's layer digests mapped to files by the repository listing (shards and the projector a vision model takes included), mlx from the listing at the revision for the pull patterns (huggingface_hub's own bars are off), basert from `basert list --remote --json`'s catalog size, else the Hub listing of a raw repository. A pull with no total shows bytes, rate and time elapsed; `--offline` draws nothing (#90).
- Fleet: a node that joins the head is listed only with its first connection in place. `FleetManager::adopt` listed a new node, then learned its meta, set its keepalive and sent the control ask before it stored the connection; a probe or placement in that window found an empty slot, took the node for one that had left and marked it down (`fleet_join::a_node_that_dials_in_is_adopted_and_serves_a_session` failed once on `ubuntu-24.04` with "left; waiting for it to join again"). The new node's first slot is now held from before it is listed until its connection is in it; the lock order is the one `keepalive` already uses (#93).
- CI: every GitHub-hosted macOS job runs on `macos-15` (`ci.yml`'s core matrix and runtime adapters, `release.yml`'s `aarch64-apple-darwin` build and `crates-verify`, `nightly-runtimes.yml`'s MLX job), since GitHub retired the `macos-14` image on 2026-11-02 and cancels jobs that ask for it. The released binary's minimum macOS stays 15.0 (`MACOSX_DEPLOYMENT_TARGET`, checked by `scripts/build_runtime_adapters.sh`) (#91).

## 0.1.7

- A fleet head runs the server one machine runs, with the same handlers, over a `Daemon` whose scheduler commands a fleet dispatcher (`fleet_daemon.rs`) answers by placing each generation on a node instead of a local engine; a lane's output is a `LaneOutput`, so channels, tool calls, stops and usage are built on the head as a local lane builds them, every decode step runs on the node, and a request's text is encoded once. Every API format and route answers through the head: OpenAI chat, completions and responses, Anthropic messages, Ollama `/api/chat` and `/api/generate`, embeddings, LoRA load and unload (on every node serving the model), images, audio and transcription (a file goes to a node once per connection by its SHA-256, in 4 MiB chunks, into the node's media pool; a streamed transcription's segments come as the node has them), structured output, `logit_bias`, `logprobs`, the penalties and `ignore_eos`; the head keeps a grammar or bias and the node compiles it, and the head describes the model as its first node does. Link F 3, negotiated down to 2 for an older peer: `GENERATE_OPTS`, `STATE_SYNC_REQ/RESP` and `STATE_SYNC_SEGMENT`, `XFER_*`, `TOKENIZER`, `TOKENIZER_EXPORT_REQ/EXPORT` and `TOKENIZE_REQ/RESP`, and `CONTROL_ASK`, a droppable message that asks a joined node for one connection more than its lanes, for short calls while every lane generates (a listed node keeps one too). `--model` is given once per model: each is announced over mDNS, a request's `model` picks the nodes serving it, `/v1/models` lists each, and a node whose tokenizer digest differs from the head's for that model gets none of its requests. ## 0.1.0

First public release.

- `superfluid serve <model>`: one daemon serving GGUF files through llama.cpp, MLX directories through MLX and `.base` bundles through the baseRT engine, each runtime installed on first use.
- OpenAI-compatible chat, completions, embeddings, files, batches and Responses API; Anthropic Messages API; Ollama API; a native session API over a unix socket and WebSocket, with a Python client (`clients/python`).
- Continuous batching with QoS classes, per-key policy, rate limits and preemption of background work by interactive requests.
- Durable sessions in a write-ahead log: fork, resume after a restart, survive a worker crash.
- Prefix caching, KV parking, speculative decoding, tool calling and structured outputs.
- Prometheus metrics, OTLP traces and metrics, structured logs and a terminal monitor.
- Fleet mode: one head serving the HTTP API over several nodes.
