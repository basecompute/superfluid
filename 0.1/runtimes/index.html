Runtimes

A runtime runs a model's forward pass: llama.cpp, MLX, the baseRT engine, or the built-in mock. Superfluid ships an adapter per runtime and installs the runtime itself from its own project's releases. Each model runs in its own worker process, so a runtime crash restarts that worker, not the daemon.

idaliasesservescomes from
llamacppllama.cpp, llama-cppGGUF filesllama.cpp's release builds
mlxMLX directories (Apple silicon)a private CPython with mlx and mlx-lm
basertnative.base bundlesthe baseRT engine library, loaded at run time
mocknothing realbuilt in; used by the test suite

llamacpp and mlx are primitive runtimes: Superfluid's generic executor implements batching, the prefix cache, sampling, grammars and park/resume on top of them. basert is a full engine that implements all of that itself.

Managing installs

superfluid runtimes                              # state of every runtime, and the newest version each installs here
superfluid runtime versions llamacpp             # every version the adapter installs on its own: which install here, which are installed
superfluid runtime install llamacpp --dry-run    # print the plan, fetch nothing
superfluid runtime install llamacpp
superfluid runtime install llamacpp --backend vulkan
superfluid runtime update llamacpp
superfluid runtime use llamacpp b11284-vulkan    # pin the default install
superfluid runtime use llamacpp --auto           # unpin
superfluid runtime repair llamacpp
superfluid runtime remove llamacpp b11284-vulkan
superfluid runtime remove llamacpp@b11284-vulkan # the same, as `superfluid runtimes` lists the install
superfluid runtime remove llamacpp --all         # every install
commandwhat it does
versions <id>list the versions the adapter installs on its own (the ones it was tested with), newest first: which install on this machine and as what, with the size, and which are installed; an install of another version (--untested, or an archive of your own) is listed as not one the adapter lists. basert installs a release it does not pin without --untested when the release states this build's engine ABI, and with no version the newest such release: an install of one newer than the pins is listed as installable when a build for the same engine ABI installed it, and the line below the list says so. --json for scripts. Answered from the adapter's recipe and the installs, with no network
install <id>plan, fetch, verify and place an install. Options: --version V, --backend B (no fallback), --from <archive> (a URL or path to your own archive or, for MLX, package index), --sha256 H, --untested, --dry-run
update <id>install the newest tested build for the default install's backend beside it and make it the default. basert learns the newest from its release listing: when that cannot be fetched, the newest it installs on its own is a pinned release, and an install that is not older than it is left alone with exit 1 and the fetch's error, rather than reported up to date
repair <id> [<install>]reinstall the same version and backend; what a daemon updated with superfluid self update asks for when an install's worker is too old
remove <id> [<install>] / --allremove one install, or every one with --all; the id alone removes the only install and refuses a runtime that has more
use <id> <install> / --autopin the default install / return to ranking

repair, remove and use take the install as <id>@<install> too, as the RUNTIME column of superfluid runtimes shows one that is not the default.

serve installs a runtime on first use; --offline prevents it. A runtime's worker starts without credential-named variables (*_TOKEN, *_API_KEY, *PASSWORD, *SECRET, ...) in its environment; a pull keeps them, since it fetches with your Hugging Face token.

An install fetches over https:// only, checks each asset against a SHA-256 known before the fetch (the adapter's pinned one, or --sha256), stages it, and runs the staged worker's check. An archive from elsewhere with no SHA-256 to check is refused; a local file without one installs with a warning. An archive member that would land outside the install (an absolute path, .., a symlink out) fails the install. If the runtime finds no device of the planned backend, the next plan is tried (CUDA, then Vulkan, then CPU). One install of a runtime runs at a time across processes; a failed install leaves the existing ones as they were.

Where installs live

~/.superfluid/runtimes/<id>/
  <install>/              b11284-metal, 0.3.1-cuda, 0.32.2-metal
    bin/superfluid-worker-<id>
    lib/                  libraries and tools
    python/, env/         (mlx) private CPython and environment
    runtime.json          version, backend, sources with SHA-256
  current -> <install>    the default install
  pinned                  set by `runtime use`

The default install is the pinned one, else the best-ranked: a GPU backend (metal, cuda, rocm, vulkan, sycl, openvino) before cpu, then the newest version. A running daemon keeps the install it started with until it restarts.

Per-runtime installs

llama.cpp. The tested builds are the ones superfluid runtime versions llamacpp lists; another needs --untested, and the refusal says whether it lies between two tested builds, whose C API it very likely shares, or past the newest or oldest, where it may differ. The backend is chosen from the machine:

machinebuildfalls back to
macOS, Apple siliconmetal
macOS, Intelcpu
Linux with an NVIDIA drivernewest CUDA the driver runs (cuda-13.x from driver 580, cuda-12.x from 525)ROCm, Vulkan, CPU
Linux x86-64 with ROCmrocmVulkan, CPU
Linux with a Vulkan loadervulkanCPU
any Linuxcpu

SYCL and OpenVINO builds are installed only with --backend.

MLX. Apple silicon only. Fetches CPython 3.12.14 (python-build-standalone) and, from PyPI, mlx, mlx-metal, mlx-lm and their dependencies, every wheel pinned by hash (tested: mlx 0.32.2, mlx-lm 0.31.3). Installs with pip --require-hashes --no-deps --only-binary=:all:; your own Python and PYTHON*/PIP_* settings are not used (pip's network settings excepted).

basert. Engine bundles from baseRT's releases for macos-arm64 (Metal), linux-arm64-cuda (an NVIDIA GPU) and linux-x64-rocm (from baseRT 0.5.0); other machines are refused. The ROCm bundle is one engine for AMD's Strix Halo (gfx1151) and Strix Point (gfx1150), which the install reads from the GPU driver (/sys/class/kfd); it runs on AMD's ROCm 10 runtime at /opt/rocm/core-10.0, and a release's engine is not installed without it. A release is tested when the engine ABI number it publishes beside its bundles (basert-engine-abi-<N>.txt) is the one this daemon was built for, or, for a 0.3.x release, which states none, by its line; another needs --untested and may not load. With no --version, the newest tested release on baseRT's release page is installed, checked against the SHA-256 GitHub lists for its engine (the digest baseRT also publishes beside it as <engine>.sha256); the adapter also pins releases with their digests, which install the same way offline, when the release page cannot be read. A release GitHub lists no digest for, and that is not pinned, installs only with --version V --sha256 H. Instead of installing, you can name an existing library with --basert-lib or BASERT_LIB.

How a worker is found

For each runtime, first match wins:

  1. SUPERFLUID_WORKER_<ID>
  2. a runtime linked into this build (superfluid-workerd --engine <id>)
  3. superfluid-worker-<id> beside the superfluid binary (a source build)
  4. the installed runtime, $SUPERFLUID_HOME/runtimes/<id>/current/bin/
  5. the adapter a release ships in libexec/superfluid/ (can only say "not installed" and install)

--runtime llamacpp@b11284-vulkan uses exactly that install's worker.

How a runtime is chosen

  1. --runtime <model>=<id> for one model, else --runtime <id> for all; the later selector wins. auto means "by format".
  2. Otherwise a path goes to the runtime that reads its format, and an id is inferred from its name (gguf → llamacpp, mlx → mlx, else basert).
  3. A pick is validated against the model's format before anything loads:
runtime llamacpp cannot serve model.base: it reads a GGUF file, and this is a .base bundle
(pass --runtime basert, or convert the model)

superfluid runtimes <path> shows the decision without serving.

Capability records

Every loaded model is described by one JSON capability record its runtime reports. Each leaf is true, or a string saying why not. The daemon uses it to refuse unsupported requests, check startup flags, and fill the capabilities object in /v1/models.

Startup flags a runtime cannot honour are refused before the worker starts:

flagllamacpp / mlx say
--park-lossythe <id> runtime exports no lossy encoding
--kv-bits <n> (non-zero)the <id> runtime keeps its KV type per context and exposes no such knob
--speculate <strategy> (not auto/off)on llamacpp/mlx: any strategy but prompt-lookup, or prompt-lookup on a model whose state cannot cut a rejected draft

--speculate auto is never refused; a model that cannot speculate decodes plainly and the log says so.

Requests a model cannot serve are refused with a 400:

{"error": {"message": "model 'Qwen3-4B-Q4_K_M' on runtime llamacpp does not accept images: the llamacpp runtime has no media path",
           "type": "invalid_request_error", "param": "messages", "code": "unsupported_input"}}

Per-runtime options

A knob of one runtime is given to serve as --<runtime>-<name> <value>, for example --llamacpp-n-gpu-layers 20. The adapter declares its options with the shape of each value; superfluid serve checks a value against that declaration before a worker starts and forwards it to the runtime's worker as --<name> <value> from its first check on, in process or not, so --llamacpp-lib can be what makes the runtime usable here; and superfluid runtime options <id> lists them, before an install too. Each is given once: a second --llamacpp-lib is a usage error (exit 2), not an override. A flag every runtime takes stays a flag of serve: the context window (--max-context), the lanes (--max-batch), the KV precision (--kv-bits), parking and speculation.

KV state saved from a run (a parked session) is keyed by the weights and by the RoPE, YaRN and cache-type settings in effect, so a run with other settings never reads it. basert options

optionvaluedefaultmeaning
--basert-neural-engineon, offonRun part of each prefill on the Neural Engine where that is faster (Apple silicon); off runs every prefill on the GPU alone. It needs an engine that has the switch: with one that has none (BaseRT 0.4.6 and earlier, which prefill on the GPU alone), off fails the load.

Its other knobs are flags every runtime may take (--kv-bits, --prefix-blob-budget-mb) and --basert-lib.

An engine that can compile a model's Neural Engine programs ahead has them compiled after a pull, by the worker that will load the model, since macOS keeps the compiled programs for each executable: once per Mac, macOS version and Superfluid build. A load that finds them uncompiled compiles them in the background while the GPU runs the prefill alone. Nothing is compiled with --basert-neural-engine off.

How an upstream release becomes a tested one

Each adapter installs on its own only the upstream versions it was built and tested against, listed in its recipe.json; another installs with --untested and is still checked at load. A nightly job (.github/workflows/nightly-runtimes.yml) keeps those lists current: it installs the newest upstream release untested (for MLX the newest mlx with the newest mlx-lm, so a release of either is tested; an mlx-lm alone replaces its mlx's entry), runs the adapter's tests on it, and records the result. A release that passes arrives as a PR adding it to the recipe (scripts/nightly_runtimes.py <runtime> append): for llama.cpp with the size and SHA-256 GitHub lists for each of its assets, for MLX with the environment pip resolved for it on the runner, every wheel with the size and SHA-256 PyPI lists for it. A runtime's PRs come from one branch (nightly/llamacpp, nightly/mlx), one open at a time, which a newer release that passes takes over; a release whose PR was closed unmerged is not proposed again. One that fails opens an issue with the run attached (one that does not finish, cancelled or expired in the queue, records nothing); an MLX that needs a newer Python than the adapter ships fails that way, since it changes the worker's build rather than a pin. A newest llama.cpp build that fails is walked back from: the run starts another on the next-newest build the recipe does not list, at most five below the one the night began on, and the first to pass is the one proposed, with a note on the issue, so an upstream build fixed a few builds later does not hold the recipe until the next night. workflow_dispatch tests a named release instead of the newest, a declined one too, and that release alone: no walk-back.

Per-runtime limits

llamacpp

  • superfluid compat lists the llama.cpp builds this adapter was built and tested against, which it installs on its own; another build installs with --untested, and is still checked at load for the functions and parameter layouts the adapter drives.

  • A build whose C API differs from the tested one is refused by name at load. SUPERFLUID_LLAMA_LIB or --llamacpp-lib loads your own build instead of an install.

  • With no --max-context, the window is sized for the device on Metal, and on CUDA with a dedicated GPU; elsewhere it is 8192. Once a context exists, one that left the device short of its reserve is made again with fewer cells; a pool cut below one sequence serves that model at the shorter window.

  • Plain-attention models get a KV buffer per sequence (lanes plus two, at least 4, at most 256), so a decode step attends only over its own sequence. Recurrent, hybrid and sliding-window models (Qwen3.5/3.6-class, gemma) use one shared pool and reuse prefixes only at a sequence's head.

  • The prefix cache keeps at most one lane's context in a shared pool, where every step attends over the cells up to the highest one in use. The rest of the cache, and any entry that gives up its sequence to a lane, is held in host memory as llama.cpp's own state export and imported when a request reuses it: as many tokens as the pool has cells, within 8 GiB and 60% of the memory the model and its context leave free. On a host without an accelerator, or with the model on the CPU, the 8 GiB alone bounds it.

  • On Metal, a prompt batch on a shared pool is filled to a multiple of 8 tokens: the attention kernel computes a last group short of 8 queries against every cell in use.

  • No lossy park, no media, no batch invariance. Greedy rounds take llama.cpp's argmax; sampled rounds are sampled on the host.

  • llama.cpp's own log is silenced unless SUPERFLUID_LLAMA_LOG=1.

mlx

  • superfluid compat lists the MLX versions this adapter installs on its own and the Python they run on.

  • Apple silicon only. Python runs in the worker, so a Metal fault kills the worker, never the daemon.

  • Greedy and sampled rounds run on the device, one step ahead.

  • A joining request's prompt runs between decode rounds; lanes already decoding pause for it.

  • With no --max-context, the window is sized for the device from what the worker reads off the model without loading it (superfluid-worker-<id> check --model <path> shows it as sizing).

  • Recurrent models reuse prefixes only at a sequence's head, and from copies of the state kept where each prompt of 128 tokens or more ends (one token short) and where requests queued behind a prefilling lane stop sharing its prompt (1024 tokens or more), so a resent prompt, a next turn that repeats it, or a burst on one long prefix starts there. No lossy park, no media, no batch invariance.

  • A directory whose config.json names its own code is refused unless SUPERFLUID_MLX_TRUST_MODEL_CODE=1.

  • A load is refused unless weights plus a tenth plus 1 GiB fit in available memory while leaving the larger of 4 GiB and a tenth of RAM free. SUPERFLUID_MLX_SKIP_FIT_CHECK=1 overrides.

basert

  • The engine library is loaded at run time. A library of baseRT 0.4.0 or later states an engine ABI number, which must equal the one the daemon was built against, whatever the versions say; a 0.3.x library states none and is accepted as the line that carried that ABI before it was numbered. superfluid compat prints what the daemon drives. superfluid runtime install basert picks an engine by the number baseRT publishes beside each bundle.
  • What a bundle supports (speculation, media, embeddings, lossy parking) is known only once it is loaded.
  • Serving .base bundles needs a daemon built with the default basert feature; only the engine tokenizes them.
  • Pulling by id needs the basert tool (BASERT_CLI, beside libbaseRT, or on PATH).
