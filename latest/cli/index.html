Command-line reference

superfluid is one binary with a few subcommands. Environment variables and the on-disk layout are in Configuration.

commandwhat it does
superfluid serve <model>run the server
superfluid launch <agent>run a coding agent against a local model, starting a server if none answers
superfluid stopstop the server launch started
superfluid fleet tokenprint the fleet token, making it the first time
superfluid node join [<head>] --model <m>serve a model to a fleet head from this machine
superfluid runtimes [<model>]list runtimes, or say which one serves a model
superfluid runtime <subcommand>install, update, repair, remove or pin a runtime
superfluid compatwhat this build was built for: the runtime contracts it checks at load
superfluid self <subcommand>update Superfluid itself, or switch between the versions installed here
superfluid session <subcommand>inspect or export a session from a running server
superfluid media <subcommand>store media in, or sweep, a running server's media pool
superfluid top [<host:port>...]live monitor over one or more servers, or a fleet
superfluid --help                 # command overview (also: superfluid, superfluid help)
superfluid serve --help           # every serve flag, grouped, with its default
superfluid help runtime           # one command's help
superfluid --version              # also -V, superfluid version

Flags take their value as --flag value or --flag=value. The last occurrence of a scalar flag wins; repeatable flags accumulate.

Exit codes

codemeaning
0normal exit (closed socket, quit monitor, finished drain)
1run-time failure: a port or socket that cannot be bound, a sessions directory another server holds, a damaged session log, a worker that did not start, a model that did not load, a failed install or pull, a shipped adapter that did not answer compat
2usage or configuration refusal, before anything loads. An unknown flag names the closest valid one; a bad value names the flag and what it expected
3(superfluid-workerd, superfluid-noded) the model did not load
4(serve) the runtime for the model is not installed or cannot run here: its engine library is missing or of another ABI. A host that starts Superfluid can tell this from a flag it got wrong (2), and from an install Superfluid tried that failed (1)

superfluid serve

superfluid serve <model> [--model <model> ...] [flags]

A model is a path or a Hugging Face-style id org/model[:tag]. Everything else has a default: the session log goes to ~/.superfluid/sessions, the session socket to ~/.superfluid/superfluid.sock, and the HTTP API listens on 127.0.0.1:8453. A runtime that was never installed is installed on first use.

superfluid serve unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_M        # llama.cpp
superfluid serve mlx-community/Qwen3-4B-4bit           # MLX (Apple silicon)
superfluid serve ./Qwen3-4B-Q4_K_M.gguf                 # runtime picked by format
superfluid serve ./model.gguf --port 9000 --api-key "$KEY" --max-batch 4

Model

flagdefaultdescription
--model <model>requiredA model path or id to serve; repeatable. A bare first argument is the same. The first model is the default for requests that name none.
--runtime <id>[@<install>]inferredRuntime for every model: basert, llamacpp, mlx (aliases native, llama.cpp, llama-cpp); auto clears it. Repeatable.
--runtime <model>=<id>[@<install>]Runtime for one model, named by path, file stem or id.
--offlineoffFetch nothing: look for an id only where its runtime keeps models, and install no runtime.
--pull-<name> [value]Pass --<name> to the runtime's pull tool (for example --pull-file model.gguf). See Supported models.
--<runtime>-<name> <value>the runtime'sA knob of one runtime, for example --llamacpp-n-gpu-layers 20 or --mlx-prefill-chunk 512; superfluid runtime options <id> lists them, and Runtimes describes them. The value is checked against the runtime's declaration before anything loads, and an option given twice is refused (exit 2); a flag every runtime takes (--max-context, --max-batch, --kv-bits) is never spelled this way.
--model-dir <dir>noneEvery model under <dir> becomes known and loads on first request. See Serving multiple models.
--idle-timeout <sec>0 (never)Unload a model unused this long, if it can be loaded again; never the default model.
--basert-lib <path>searchlibbaseRT file or directory for the basert runtime (sets BASERT_LIB).

With no --runtime, a model id goes to llamacpp when its repo name contains gguf, to mlx when it is mlx-community/... or its repo name contains mlx, and to basert otherwise. A path goes to the runtime that reads its format.

Retired flags

Flags from earlier releases are accepted with a notice naming what replaced them: --paged-kv, --prefix-cache, --continuous-batching [N], --prefix-cache-file, --prefix-cache-save-interval, --files-dir, --media-dir, --metallib, --prefill-chunk, --gpu-wait-timeout-ms, --decode-replay, --paged-weights, --no-paged-weights-retry, --no-baked-decode.

superfluid launch

superfluid launch                                   # list the agents and whether each is installed
superfluid launch <agent> [--model <m>] [--http <addr:port>] [--api-key <key>] [--print] [-- <agent args>...]

Runs claude, codex, pi, opencode, hermes, cline, openclaw or the ollama CLI pointed at the server on --http, starting superfluid serve <model> in the background when nothing answers there. --print shows what would run; arguments after -- go to the agent. See Superfluid launch.

superfluid stop

Sends the server launch started SIGTERM and waits for it to drain. A server started with superfluid serve is not touched.

superfluid runtimes

superfluid runtimes [<model>] [--json]

Without a model: one row per runtime and install, with state (ready, not installed, broken, missing), version, the newest version its adapter installs on its own here (INSTALLABLE, marked (installed) when an install of it exists; superfluid runtime versions <id> lists them all), formats, device and worker location, then each problem with its fix. INSTALLABLE is a version the adapter lists, or an installed one newer than all of them that the adapter installs without --untested all the same: for basert, a release that states this build's engine ABI, which superfluid runtime install basert takes with no version from the release listing (superfluid runtimes itself asks the network nothing). The device column gives its memory budget, what the runtime plans a model and its KV cache against there, by the same rule for every runtime: a share of the device's working set, 85% on Apple silicon. The worker column names an install by its name in the runtimes directory (installed: mlx/0.32.4-metal) and a worker of Superfluid's own by where it came from (built in, shipped with superfluid, beside superfluid); the release's directory and the runtimes directory are printed once below the table, and your home directory as ~. With a model: which runtime reads it and what that runtime serves and refuses; exits 1 when none here serves it.

With --json, a runtime's row carries installable, the versions its adapter installs on its own here, newest first; worker.path, the worker's whole path; and per device memory, the device's memory as the runtime reads it (llama.cpp's device total, MLX's recommended working set, baseRT's own budget), beside budget, the figure the table shows (0 where the runtime plans nothing, such as llama.cpp's CPU); a ready runtime's row carries abi when the runtime states a contract number (baseRT's engine ABI) and options when the runtime takes knobs of its own on serve (each with name, kind, choices, least and most when the value is bounded, default and about), and the basert row carries requires, what this build was built for, whether or not an engine was found. See Hosting Superfluid in another product.

superfluid runtime

superfluid runtime versions <id> [--json]
superfluid runtime install <id> [--version V] [--backend B] [--from <url|path>] [--sha256 H] [--untested] [--dry-run]
superfluid runtime update <id>
superfluid runtime repair <id> [<install>]
superfluid runtime remove <id> [<install> | --all]
superfluid runtime use <id> <install> | --auto
superfluid runtime options <id> [--json]

repair, remove and use also take an install as <id>@<install>, the way superfluid runtimes lists one in its RUNTIME column: superfluid runtime remove basert@0.3.0-metal is superfluid runtime remove basert 0.3.0-metal, and two installs named both ways are refused. The other actions take the id alone and say so.

remove <id> with no install removes the runtime's only install; when it has more, it names them and removes nothing, and --all removes every one. The bare id is also how superfluid runtimes lists the default install.

See Runtimes. options lists the knobs the runtime takes on serve as --<id>-<name> <value>, with the shape of each value and its default. It answers before the runtime is installed or runs here, from the adapter that would install it, so --llamacpp-lib can be found when the runtime needs it; see per-runtime options.

superfluid compat

superfluid compat [--json]

What this build was built and tested for, per runtime: for basert, the baseRT header version it carries, the engine ABI number it checks at load, the line accepted without one and the engines it installs on its own; for llamacpp and mlx, the upstream versions the shipped adapter installs on its own. Each shipped adapter answers superfluid-worker-<id> compat --json for its part; one that fails or does not answer within a minute is reported under its runtime as error, with the last lines it wrote to stderr, and superfluid compat then exits 1 after printing the rest. A release carries the same JSON beside its tarball as compat.json. See Hosting Superfluid in another product. For one runtime on this machine, superfluid runtime versions <id> says which of those versions install here.

superfluid self

superfluid self update [--version <v>] [--dry-run] [--yes]
superfluid self check
superfluid self list
superfluid self use <v>
superfluid self install --from <dir> [--prefix <dir>]

update installs the newest release that fits this machine beside the current one, proves it starts, and makes it current; the version it replaced stays for use. For a copy a package manager or basert installed, it runs that one's update instead (asking first, or with --yes). check asks whether a newer release is out. install places an unpacked release, which is what the install script runs. See Updating Superfluid.

superfluid session

superfluid session inspect <id> [--socket <path>] [--json]
superfluid session export <id> [--socket <path>] --format jsonl|otlp-jsonl [--out <dir>] \
    [--include-content] [--model <name>] [--endpoint <otlp-http-url> [--allow-content-egress]]

inspect prints a session's summary and events. export writes its events as JSONL or OTLP trace lines, or pushes them to a collector. Content is omitted unless --include-content, and leaves the host only with --allow-content-egress. --socket defaults to $SUPERFLUID_HOME/superfluid.sock. See Sessions.

superfluid media

superfluid media put <file> [--socket <path>]    # store a file, print its hash
superfluid media gc [--socket <path>]            # sweep blobs no session references

superfluid top

superfluid top [--api-key <key>] [<host:port> ...]

Live per-node view over each server's /metrics. A fleet head's address stands for every node joined to it, and rows appear and go as nodes join and leave. With no address, top finds the fleet head on the local network. A keyed server needs --api-key, else it shows as 401. q or Esc quits.

superfluid-workerd and superfluid-noded

superfluid-workerd is the worker the daemon spawns per model; you do not run it to serve. superfluid-workerd check --engine <id> prints the runtime report superfluid runtimes reads. Installed runtimes ship their own workers (superfluid-worker-llamacpp, -mlx, -basert) with the same interface; see Writing a runtime adapter.

superfluid-noded is the fleet node agent; its flags are in Distributed serving.
